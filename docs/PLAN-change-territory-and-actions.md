## 2. Workstream B — making change visible

**The owner's words:** *"I can't tell based on all the different scans what new features or new
comments are being discussed… over time, be able to track sentiment if it's staying the same, if
it's increasing… I need to be able to drill down specific source or the product or whatever it is
and see are we making it better?"*

Three distinct questions. The plan answers each separately rather than with one chart.

| Question | Answer surface |
| --- | --- |
| What is new since last week? | New topics, new signals, first-seen dates |
| Is it getting better or worse? | Sentiment and index deltas, period over period |
| Better or worse **for what**? | The same numbers, broken down by source, product and territory |

### 2.1 Decision: compute on read, do not persist a cluster-history table

The obvious move is a `topic_clusters` daily snapshot table. **Reject it, for now.**

Everything needed is already derivable and deterministic:

- **"New this week"** = topics whose earliest carrying signal falls inside the window.
  `sentiment_results.topics` is a `text[]`; `unnest` + `MIN(published_at)` grouped by topic
  answers it exactly.
- **"Damage as of date D"** is a pure function of the signals published before D and their
  distance from D — `recencyWeight(publishedAt, asOf)` in `libs/scoring/src/score.ts:19`. It is
  reproducible for any past date from data we already hold.

A snapshot table would add a migration, an hourly write amplification of (topics × brands), and a
second home for a number that can drift from its source — the exact failure `signals` already
suffered with its denormalised sentiment columns (KNOWN-GAPS #11), and which
`PLAN-product-hierarchy.md` §2.3 rejected for the portfolio index on the same grounds.

**Revisit when, not if.** Persist a snapshot the moment either holds, and not before:

- a single brand exceeds ~50,000 signals inside the 360-day window, or
- p95 on `/brands/:id/whats-new` exceeds 500 ms in the deployed environment.

Record the measurement in the PR that changes the decision. Until then, on-read cannot drift and
costs one migration less.

### 2.2 `ingested_at` vs `published_at` — both, and labelled

These answer different questions and conflating them is how a "new this week" panel lies:

- **`ingested_at`** — *what we learned this week.* A review written in March that a newly
  connected feed surfaced today is new **to us**. This is the honest column for "across a week
  worth of scanning what is new", which is what was asked for.
- **`published_at`** — *what the world said this week.* This is the right column for trend,
  because backfilling a March review must not create a spike in August.

Default the "what's new" surface to `ingested_at`, the trend surfaces to `published_at`, and say
which is which in the UI. A signal whose two dates differ by more than 7 days is worth marking as
*backfilled* rather than *new*.

### 2.3 API

All four are additive. No existing response shape changes.

```
GET /brands/:id/whats-new?days=7&territory=&source=&basis=ingested|published
    → { window: {from,to,basis},
        newTopics:      [{topic, volume, sentiment, firstSeenAt, sampleSignalIds[]}],
        risingTopics:   [{topic, volume, previousVolume, sentiment, previousSentiment, delta}],
        fallingTopics:  [ …same… ],
        signalsNew: n, signalsPreviousPeriod: n,
        sentimentDelta: number|null,
        bySource: [{source, volume, previousVolume, sentiment, previousSentiment}] }
```

`sentimentDelta` is `null`, never `0`, when there is no comparison period. That distinction was
already got wrong once — the `▲ +0` fixed on 2026-08-10 — and `DimBar` already renders
`prev === null` as *no prior data*. Reuse it.

```
GET /brands/:id/trend?by=source|product|territory&days=90&dimension=
    → [{ key, label, points: [{date, score, signalCount}] }]
```

`by=product` reads the entity's children and uses `attributedTo()` per child, so a product
mentioned in a group-level article counts — matching the rollup, not `readScoredItems`. See §5.2.

```
GET /brands/:id/anomalies
    → [{ dimension, current, baseline, delta, breached, thresholdPoints, windowHours }]
```

Spec §5.5's rule: rolling 24-hour mean against the 30-day baseline, default threshold 15 points,
configurable per tenant later. Detection only — no email, no webhook.

`/brands/:id/stats` gains the funnel described in §5.3.

**Every one of these needs `requireBrandAccess` as a `preHandler` and a `tenant_id` filter in its
`where`.** Tenant scoping here is opt-in and nothing fails when a new route omits it — that is
precisely how `GET /brands/:id` kept an intra-tenant hole (KNOWN-GAPS #5), and how the content
backfill route shipped with no tenant filter at all in August. Add a route-level test for each
that asserts a second tenant's brand returns 403.

### 2.4 Web

- **Dashboard** — a *Since last week* strip above the fold: signals collected, net sentiment
  move, count of new topics, and the single biggest riser. Each is a link into the drill-down,
  not a dead number.
- **New view: "What's changed"** (nav group *Intelligence*, after *Brand impact*). Three columns —
  new, rising, falling — each card opening the existing cluster drill-down so the verbatim
  evidence is one click from the claim. This is the view that answers the owner's question
  directly.
- **Trends** — a `by source | product | territory` selector driving `/trend`. The existing
  `LineChart` in `components/charts.tsx` already takes a flat row per point and a series list;
  no new chart component.
- **Anomaly badge** on the dimension bars where `breached` is true. No banner — `KNOWN-GAPS.md`
  #13 records the anomaly banner being removed for having nothing behind it, and a badge that
  appears only on a real breach does not repeat that.

Styling: CSS custom properties only. Literal hex breaks the runtime palette switcher, which
KNOWN-GAPS #19 and #20 both bit on.

### 2.5 Tests

- `libs/scoring` — pure unit tests for the new period-comparison helpers, including: empty prior
  period → `null` not `0`; a topic present in both periods is not "new"; a topic whose only
  signals are backfilled is not "new" under `basis=ingested`.
- `apps/api` — route tests per endpoint, each with a cross-tenant 403 case. **At least one must
  run against real Postgres, not a mock.** Two shipped defects in this repo were invisible to
  mocked tests because a mocked database never renders SQL (`DEVRULES.md`, the `Date`-in-`sql`
  rule); `apps/api/test/routes/keyset.test.ts` is the shape to copy.
- `apps/web` — component tests for the new view's three states, plus a Playwright spec in
  `apps/web/e2e` that opens *What's changed* and clicks through to verbatim evidence.

### 2.6 Estimate

**4–6 days.** No migration, no infrastructure change. The `by=product` breakdown and the
territory parameter are the two places where care costs more than typing.

## 3. Workstream C — an action roadmap that recommends an action

**The owner's words:** *"You've got three tiles suddenly saying what to fix first. that just goes
back to telling me what the feedback is. There's nothing there that is an actual plan on how to
fix these things."*

Correct. `toActionCards` (`apps/web/src/lib/brand-data.ts:265`) re-labels a damage-ranked cluster
as an "action". The card says *"12 signals mention this, and it accounts for 34% of the damage"*.
That is a restatement of the complaint, not a response to it.

### 3.1 The producer is `apps/report-worker`

Per spec §5.6 and §7.3, and §0.4 above. This is the largest piece of work in the plan because
that service is currently 20 lines.

Needed:

1. **A generation path.** A scheduled weekly invocation plus an on-demand route, following the
   pattern already proven by `POST /rollup` on ingestion and the two `aws_scheduler_schedule`
   resources in `infra-aws/stack/scheduler.tf`.
2. **Bedrock wiring.** `libs/llm` already provides `getLlmClient().structured()` with forced tool
   use. Use it — the scorer's schema-forced call is the pattern, and it exists specifically so no
   code parses prose out of a model response (KNOWN-GAPS #9).
3. **A model id verified at the moment of use.** Never written from memory: this repo has shipped
   one retired id and one that never existed. `aws bedrock list-inference-profiles --region
   eu-west-2` lists them; **only an actual invoke proves access** —
   `OWNER-ACTIONS.md` §1 records two AWS "availability" fields that reported `NOT_AVAILABLE` for
   models that answered fine. A stronger model than the scorer's is right here: this runs weekly
   per brand, not per signal.
4. **ECS service, task role, log group, and a `report_worker` schedule** in `infra-aws/stack/`.
   Blast-radius analysis written **before** the apply, per `CLAUDE.md`.

### 3.2 The one owner decision: what "impact" may claim

Spec §7.3 wants "the estimated impact on the Brand Perception Score". The 2026-08-09 decision
deleted exactly that field as fabrication. Three ways to reconcile:

| | What it does | Verdict |
| --- | --- | --- |
| **(a) Omit impact** | Status quo. Share of damage only. | Honest, and the reason the owner says the page is useless |
| **(b) Computed counterfactual** ← recommended | Recompute the composite with this cluster's negative signals neutralised: *"resolving this would move your index from 62 to 65"* | **Arithmetic on real signals, not a guess.** Satisfies the spec without inventing a number |
| **(c) Ask the model for an impact estimate** | An LLM guesses a point value | Fabrication. Reject — this is what was deleted |

**(b) is recommended.** It re-runs `compositeScore` over the existing rollups with one cluster's
items excluded — the function is already pure and already exported. Label it *if resolved*, show
both numbers, and never present it as a forecast. It is a sensitivity calculation, and it is
defensible in front of a client precisely because the arithmetic can be shown.

Revenue uplift stays deferred, as the spec itself says.

### 3.3 The recommendation itself

The model is given, per cluster: the topic, its volume, its sentiment distribution, its
dimensions, the counterfactual from §3.2, and **the verbatim text of up to N contributing
signals** — which only became possible when `signals.content` landed on 2026-08-10. Before that
there was nothing to reason over but a topic tag, which is why no producer was ever written.

Forced-tool schema, no prose parsing:

```
{ headline, whatPeopleAreSaying, recommendedAction[], owner, horizon,
  confidence, evidenceSignalIds[] }
```

- `recommendedAction` is 2–4 concrete steps in the language of a channel manager, not an
  engineer. The audience is a marketing and social media team.
- `owner` is a suggested function (*support*, *product*, *content*, *pricing*) — a routing hint,
  not an org chart the product does not have.
- `horizon` is `now | this quarter | watch`.
- `evidenceSignalIds` **must** resolve to real rows for this brand and tenant, and every one is
  validated against the database before the row is written. A recommendation citing a signal that
  does not exist is worse than no recommendation, and the scorer's mention handling already
  establishes the rule: the model returns names, code resolves ids, unknown values are refused
  (`apps/sentiment-worker/src/scorer.ts:30`).

### 3.4 Persistence — migration `0015`

```
recommendations
  id                uuid pk
  tenant_id         uuid not null references tenants(id)
  brand_entity_id   uuid not null references brand_entities(id)
  topic             text not null
  territory         varchar(16) not null default 'all'   -- see §4
  headline          text not null
  body              jsonb not null        -- the structured object above
  evidence_ids      uuid[] not null
  impact_from       real, impact_to real  -- the §3.2 counterfactual, nullable
  model_version     varchar(100) not null
  generated_at      timestamptz not null default now()
  superseded_at     timestamptz
  unique (brand_entity_id, topic, territory, generated_at)
```

Stored rather than generated on read for four reasons: the spec says actions persist *between*
reports; a recommendation that changes wording on every page load cannot be trusted or actioned;
it is the audit trail the product's whole pitch rests on; and it makes the weekly LLM spend
weekly rather than per page view.

`superseded_at` rather than deletion — a superseded recommendation is how "did we act on this,
and did it work" becomes answerable later.

`tenant_id` denormalised, for the reason given on `signal_mentions` and
`conversation_messages`: no row-level security exists, so the safe query must not require a join
to be safe.

### 3.5 Web

`RoadmapView` renders the stored recommendation: headline, what people are saying, the numbered
steps, the *if resolved* delta, suggested owner and horizon, and the evidence — opening the
existing drill-down at the cluster. Keep the "read the original ↗" link on each cited signal;
the owner was explicit that the in-app text is *as well as* the source link, not instead of it.

An empty state that distinguishes *not generated yet* from *nothing to recommend*.

### 3.6 Estimate

**6–9 days**, of which roughly half is standing up `report-worker` as a real service with its
Terraform. Gated behind Bedrock access on a model actually invoked, not merely listed.

## 4. Workstream A — territory

**Purpose:** answer "how is Tes seen **in Australia**", and make the Country column in
`Tes Social Channels.md` mean something.

### 4.1 Decision: territory is a property of the **feed**, not the brand

A brand is not British. A *feed* is: `@TeachStarterUSA` is US, `@TeachStarter` is AU, and both
belong to the same product. The sheet is organised exactly this way — one Country per channel —
and `source_configs` already carries per-feed configuration, including a `country` inside the App
Store adapter's config blob today.

### 4.2 Decision: denormalise onto `signals`

`source_configs.territory` is the authority. It is **copied onto `signals.territory` at insert**,
for three reasons:

1. `signals.source_config_id` is nullable and `ON DELETE SET NULL` — deleting a feed would erase
   the territory of every signal it ever collected. That history belongs to the brand, not to the
   configuration, and the column comment already says so.
2. Every rollup and trend query filters on it; a join per query for a value that never changes for
   a given row is waste.
3. Same rule as `tenant_id` on `signal_mentions`: the safe query must not require a join.

Retroactively changing a feed's territory does **not** rewrite history. A signal was collected
from a feed that was UK at the time. Correcting a mistake is an explicit backfill, not a side
effect — and that must be stated in the UI when the field is edited.

### 4.3 Schema — migration `0014`

```
source_configs.territory   varchar(16) not null default 'unknown'
signals.territory          varchar(16) not null default 'unknown'
dimension_scores.territory varchar(16) not null default 'all'
```

**The unique constraint on `dimension_scores` must change** from
`(brand_entity_id, date, dimension)` to `(brand_entity_id, date, dimension, territory)`.

> **`territory` on `dimension_scores` is `not null` with an `'all'` sentinel, deliberately.**
> Postgres treats NULLs as **distinct** in a unique constraint, so a nullable territory column
> would silently permit unlimited duplicate rows for the aggregate — the rollup upsert would stop
> upserting and start appending, every hour, forever, with no error. `NULLS NOT DISTINCT` exists
> in PG 15+ but pins behaviour to a server version. A sentinel does not.

Index: `dimension_scores (brand_entity_id, territory, date)` — the trend query's access pattern.

### 4.4 Vocabulary — ISO 3166-1 alpha-2, plus two sentinels

`GB`, `US`, `AU`, … plus `GLOBAL` (a genuinely worldwide account) and `unknown` (not yet
classified). Store the code, label it in the UI — the sheet says "UK", ISO says `GB`, and storing
the display string would guarantee `UK`/`United Kingdom`/`uk` all appearing within a month.

> **Six rows in `Tes Social Channels.md` say `Global?` with a question mark** — Tes Magazine
> (Facebook), Tes Staff, Master Timetablers, Orovia Education ×2, Tes Resources, and three
> YouTube channels. That is ambiguity in the source data. **Do not guess it.** Import them as
> `unknown` and put the list in `OWNER-ACTIONS.md` for the marketing team to settle. A wrong
> territory produces plausible, silently misattributed reporting — the same failure mode as the
> YouTube channel-id near-miss recorded in `OWNER-ACTIONS.md` §5.

### 4.5 Backfill

One-off, resumable, tenant-scoped, following `apps/api/src/routes/backfill.ts` — including the
lesson from that route, which shipped querying **every** tenant's signals.

- `signals` with a `source_config_id` inherit that feed's territory.
- `signals` without one become `unknown`. There are signals predating the column; inventing a
  territory for them would be fabrication.
- Existing `dimension_scores` rows become `'all'`, which is what they are.

### 4.6 Rollup

`rollupDimensionScores` gains an inner loop: for each brand, once for `'all'` and once per
territory present in that brand's signals. Cost is `brands × (territories + 1)` queries where it
is `brands` today. At current scale (a handful of brands, four territories) that is fine; if brand
count grows, the loop becomes one grouped query rather than N.

Territories are derived from the data present, not from a fixed list — a brand with no Australian
feed gets no Australian rows, rather than a row of nulls.

### 4.7 API and web

- `?territory=` on `/score`, `/dimension-scores`, `/brand-impact`, `/topics`, `/strengths`,
  `/stats`, `/signals`, and all of §2.3's endpoints. Absent means `'all'` — every existing caller
  keeps working unchanged.
- Admin → Feeds gains a territory selector, and the feed list shows it. Validate against the
  vocabulary server-side; an unrecognised code is a 400, not a stored typo.
- A territory switcher in the shell beside the brand switcher, defaulting to *All territories*.
  It belongs in `brand-context.tsx` so every view reads one source of truth rather than each
  holding its own state.
- The territory must appear **in the drill-down evidence**, next to the source badge. A user
  filtering to Australia has to be able to confirm that what they are reading is Australian.

### 4.8 Estimate

**3–5 days.** Two migrations' worth of care in one, a backfill, and a parameter threaded through
eleven endpoints and six views. The unique-constraint change in §4.3 is the part to get right
first time.

## 5. Workstream D — the rollup that misses brands

MyConcern (6 signals) and Provision Map (10 signals) have zero `dimension_scores` rows.

### 5.1 Diagnose before fixing

`rollupDimensionScores` `continue`s when `scoreAllDimensions` returns `[]`
(`apps/ingestion/src/rollup.ts`). That happens under three distinct conditions, and they need
different fixes:

| Hypothesis | How to confirm | Fix |
| --- | --- | --- |
| Signals were never scored — no `sentiment_results` row, so the `innerJoin` drops them | `COUNT` signals left-joined to `sentiment_results` where the result is null, per brand | The `/reconcile` sweep already exists for exactly this; find why it did not fire |
| Scored, but `dimensions` is `[]` | `COUNT(*) WHERE cardinality(dimensions) = 0`, per brand | §5.3 |
| `published_at` older than 360 days | `MIN(published_at)` per brand | Lookback is deliberate; surface it rather than change it |

**This requires live database access — `aws sts get-caller-identity` currently fails with
`Token has expired and refresh failed`.** Run `aws sso login --profile psignal-dev` first, and
confirm the identity resolves to `290304998906` before any AWS call.

### 5.2 A defect found while reading this code, unrelated to the report

**The index and the evidence behind it are computed from different populations.**

- `apps/ingestion/src/rollup.ts:50` counts a signal toward a brand via `attributedTo()` —
  the foreign key **or** a `signal_mentions` row.
- `apps/api/src/routes/scores.ts:410` (`readScoredItems`, feeding `/brand-impact`, `/topics`,
  `/strengths`) and `:383` (`/stats`) filter on `eq(signals.brandEntityId, …)` **only**.

So a product discussed in group-level articles scores on the dashboard while its drill-down and
its signal count show far less, or nothing. That is the same class of defect as KNOWN-GAPS #26 —
the drill-down contradicting the number it was drilling into — reintroduced through a different
door.

**Fix:** export `attributedTo()` from a shared place and use it in both. It currently lives in
`apps/ingestion/src/rollup.ts` and the API cannot import from another app, so it moves to
`libs/db` (it is a query predicate over two tables in that schema) with tests asserting both call
sites produce the same population for the same brand.

This is a correctness fix and is **not** optional under the zero-technical-debt rule. It is also
plausibly a contributing cause of the reported symptom, which is why it belongs in this
workstream rather than a separate one.

### 5.3 Make the silence audible

A signal scored with no dimensions contributes to no dimension, no composite, no cluster and no
drill-down. It is collected, paid for, scored, and then invisible. Two changes:

1. **Require at least one dimension** in `SENTIMENT_SCHEMA`
   (`apps/sentiment-worker/src/scorer.ts:78`) — `minItems: 1` and a prompt line saying the text
   must be assigned to its closest dimension even when weakly related.
2. **Expose the funnel** on `/brands/:id/stats`: `collected → scored → classified → in rollup`.
   `scoredSignals` exists; the last two do not. Rendered on the Dashboard as a coverage strip so
   a brand falling out of the rollup is visible the day it happens, rather than being noticed by
   the owner weeks later. This is the change that stops this bug recurring in a new form.

### 5.4 Estimate

**1–2 days**, plus diagnosis time gated on SSO.

## 6. Workstream E — the `01` spines

Reported: every spine in the drill-down reads `01`.

The code looks correct — `DrillDown.tsx:433` is
`String(i + 1).padStart(2, '0')` over the path index, rendered at `:455`. So either the

## 7. Workstream F — KNOWN-GAPS #28, the "raw" payload that is neither

`apps/ingestion/src/handler.ts:192` writes the S3 object under a key derived from the item's
external id, so re-collecting **overwrites** it — and what it writes is `item.text`, which the
adapter has already normalised. The comment block at that line documents this honestly. It is the
reason a duplicate-headline fix could not repair its own data: the source it re-read had itself
been rewritten.

Two changes, both wanted:

1. **Carry the untouched string.** Adapters keep the source's original bytes and the payload
   becomes `{ rawText, text, … }` — `rawText` verbatim, `text` normalised. This is the actual fix:
   it restores a real audit trail and makes future normalisation changes re-derivable.
2. **Versioning on the raw bucket**, in Terraform, with a lifecycle rule expiring noncurrent
   versions (90 days is a reasonable opening position). This is the safety net for overwrites
   generally. **It has a cost implication and it changes a bucket shared in a sandbox with
   co-tenant projects — blast-radius analysis written before the apply, per `CLAUDE.md`.**

Fold this into Workstream A's ingestion change: both touch `handler.ts`'s insert path, and one
deploy is better than two.

**Estimate: 1–2 days.**

## 8. Workstream G — CRM as a signal source (HubSpot / Salesforce)

**Requested 2026-08-17:** *"a key source of signalling could also be what the Sales and Customer
Value / Customer Success team hears directly from clients in their daily interactions… This
additional 'area' may in fact need its own area as well, with filtering, reporting etc."*

The instinct that it needs its own area is right, and §8.4 makes precise *why* — it is not a
presentation preference, it is a correctness requirement.

### 8.0 Prior art

`Project-Signal-Product-Spec.md` §8 defers **"Support ticket integrations — Zendesk, Intercom,
Freshdesk. OAuth connectors, one per platform."** That is the same class of work — private,
per-tenant, OAuth — and it is the only place the architecture contemplates it. CRM itself is not
mentioned anywhere in 6,686 lines of planning documentation. This is new.

### 8.1 Why this is not "one more adapter"

Every source today is **public, pull-based, and authenticated with one system-wide credential**.
`getSystemCredentials()` (`apps/ingestion/src/handler.ts:40`) hands every tenant the same Apify
token and the same YouTube key. Three properties of CRM data break that model, and each breaks a
different part of the system:

| Property | What it breaks |
| --- | --- |
| **Per-tenant OAuth with rotating refresh tokens** | The credential model. §8.2 |
| **Contains personal data about named individuals** | The data-residency premise, retention, and access. §8.3 |
| **The voice is second-hand and self-selected** | The Brand Perception Index itself. §8.4 |

The third is the one that would do silent damage, so it is the one to settle first.

### 8.2 The credential break — `crm_connections` and Secrets Manager

A CRM connection is per tenant, obtained by an OAuth flow, and its refresh token rotates. It
cannot live in `source_configs.config`: that column is plain JSONB, unencrypted, readable by
anyone with database access, and trivially dumped into a log by a careless `SELECT *`. It cannot
live in environment variables either — those are one per deployment, not one per tenant.

```
crm_connections
  id                 uuid pk
  tenant_id          uuid not null references tenants(id)
  provider           varchar(16) not null          -- 'hubspot' | 'salesforce'
  instance_url       text                          -- Salesforce is per-instance
  secret_arn         text not null                 -- the token lives HERE, never in this table
  scopes             text[] not null
  connected_by       varchar(128) not null
  status             varchar(16) not null default 'active'
  last_synced_at     timestamptz
  last_attempted_at  timestamptz
  last_error         text
  created_at, updated_at
  unique (tenant_id, provider)
```

Tokens go in **AWS Secrets Manager**, one secret per connection, created by Terraform with the
value written at connect time by the API — the same split `infra-aws/stack/secrets.tf` already
uses, where Terraform owns the secret and deliberately does not own its value. The task role gets
`secretsmanager:GetSecretValue` scoped by name prefix, not `*`.

`last_attempted_at` / `last_error` mirror `source_configs` deliberately: a connection whose
refresh token has expired must show *why* on the row someone can fix, not read as "never synced".
That exact defect has already been fixed once on feeds.

**No token, refresh token, client secret or instance credential is ever committed, logged, or
written into a document.** `CLAUDE.md`, without exception.

### 8.3 The data-protection break — a stated premise stops being true

`docs/HANDOVER.md` §3 records the reasoning behind letting Bedrock inference route across EU
regions:

> **Note this is EU, not UK** — worth confirming against your residency requirement, though what
> crosses a border is **public review text, not personal data**.

**CRM notes are personal data.** They name client contacts, their employer, their job, and
commercially sensitive detail about a live relationship. The premise that decision rested on does
not survive this workstream, and the decision therefore has to be re-taken rather than inherited.

Four consequences, none of which are an engineer's call:

1. **Inference routing.** `eu.` profiles route to seven EU regions. Whether TES may send client
   personal data to them is a data-protection question.
2. **Retention.** Spec §6.2 sets 12 months on raw items. Personal data needs a defined retention
   period and an actual deletion path — neither exists today.
3. **Right to erasure.** There is currently no way to delete a signal by the person it concerns.
   For public review data that is arguably moot; for CRM notes it is not.
4. **Access within a tenant.** Every user of a tenant can read every signal. A CSM's note about a
   named account is not obviously appropriate for everyone with a login.

**Recommended engineering position, subject to sign-off: pseudonymise at ingest.** Strip contact
names, email addresses and phone numbers from the text *before* it is written to S3, stored in
`signals.content`, or sent to Bedrock — keeping the **account** (the company) attribution, which
is the only part the analysis actually needs. This removes most of the compliance surface at no
analytical cost.

> **This is a hard gate.** It needs the TES data protection officer, and it is calendar time
> rather than engineering time — so it should be started **now**, in parallel with the earlier
> workstreams, not when G's code is ready. It is the single longest lead item in this plan.

### 8.4 The correctness break — reported voice is not direct voice

A Customer Success manager writes a note **because something needs attention**. That makes CRM
sentiment a *work queue*, not a *sample*. It is structurally negative-biased, and the bias is not
a flaw to correct — it is what the channel is for.

Averaging it into the Brand Perception Index would drag the index down for reasons that have
nothing to do with brand perception changing, and **nobody would be able to see why**, because
the number would still look entirely plausible. That is the most expensive kind of defect this
project produces.

Two schema changes make the distinction explicit rather than a convention someone later forgets:

```
signals.voice varchar(16) not null default 'direct'   -- 'direct' | 'reported'
```

- **`direct`** — the customer wrote the words. Every public source.
- **`reported`** — an employee wrote down what a customer said. CRM, and later any support-desk
  integration.

**The Brand Perception Index is computed over `direct` only, by default.** `reported` is scored,
stored, trended and drillable on its own terms, and can be included explicitly with a visible
toggle that says what it changes. This is the "own area" the owner asked for, expressed as a
data rule rather than a menu item.

**The scorer needs a second prompt.** Today it opens *"Analyse the brand sentiment of the
following customer review"* (`apps/sentiment-worker/src/scorer.ts:38`). A CRM note is not a
review. The `reported` prompt must ask the model to score **the customer's** sentiment as
relayed — explicitly not the note-writer's tone, and ignoring internal commentary such as next
steps and account admin. Same forced-tool schema, different framing.

### 8.5 The new axis — accounts

A CRM signal is about a **customer account**, which is orthogonal to brand, product and
territory. Reusing `brand_entities` was considered and rejected: a customer is not a brand, and
putting hundreds of them in that tree would pollute the brand switcher, the portfolio rollup and
competitor comparison all at once.

```
accounts
  id, tenant_id, provider, external_id, name, domain,
  segment, arr_band, owner_name, territory, created_at, updated_at
  unique (tenant_id, provider, external_id)

signals.account_id uuid null references accounts(id)    -- null for every public signal
```

`arr_band` is a **band** (`<10k`, `10–50k`, `50–250k`, `250k+`), not a figure. It makes
"weight this theme by commercial exposure" possible without importing revenue data — which spec
§8 defers pending an open question, and this stays on the correct side of that line.

**Weighting:** in this area, rank themes by **distinct accounts affected and ARR band**, not by
raw volume. One renewal-risk note from a 250k+ account is not one-fiftieth of fifty app-store
reviews, and treating it that way is how the area would become useless to the people who asked
for it.

### 8.6 What to pull, and what not to

| | HubSpot | Salesforce |
| --- | --- | --- |
| Interactions | Engagements — notes, calls, meetings — on Company and Deal | `Task` / `Event` activity records |
| Support | Tickets | `Case` + `CaseComment` |
| Incremental key | `hs_lastmodifieddate` | `LastModifiedDate`, or Change Data Capture |
| Account object | Company | `Account` |

**Confirm every object, field and endpoint against current vendor documentation at the moment of
implementation.** The table above is a design sketch, not a verified API contract. This repo has
shipped one retired model id and one that never existed by writing from memory; the rule applies
to third-party APIs identically.

**Deliberately not pulled:** email bodies in bulk (an enormous personal-data surface for very
little signal), attachments, and contact records beyond the account association. Each is a
compliance cost with no analytical return.

The `since` watermark works exactly as it does for feeds today — per connection, not per
provider — and for the same reason recorded in `getLastIngestedAt`.

### 8.7 The area itself

New nav group **Voice of the customer** (`config/navigation.tsx` is data — adding it is a line),
holding a view that public-source data cannot fill:

- Filter by account, segment, ARR band, CSM owner, territory and date.
- Themes ranked by **accounts affected × ARR band**, per §8.5.
- A renewal-risk lens: accounts whose reported sentiment is deteriorating over time.
- **Cross-channel corroboration — "themes appearing in BOTH public reviews and CSM notes".**

That last one is the actual prize, and it is worth stating plainly: it is not achievable from
either channel alone. A complaint that shows up independently in public reviews *and* in what
customers tell their account manager is the highest-confidence finding this product can produce,
and it is the thing that would let a channel manager walk into a meeting and be believed.

Role visibility is an open question flowing from §8.3(4) and needs the same sign-off.

### 8.8 Explicitly out of scope: write-back

Pushing a Signal finding back into HubSpot as a task is tempting and is refused for now. It is a
**write into the company's system of record for its commercial relationships**, it needs a
separate OAuth scope, and a bug in it creates noise in somebody else's daily workflow. Read-only
until the read side has earned trust.

## 10. What this plan deliberately does not do

- **No new source adapters.** 84 of the 92 rows in `Tes Social Channels.md` need a paid Apify
  plan, and the popular actors refuse API access on the free tier as a matter of the author's
  policy. Writing a scraper mapper against a guessed payload is the fabrication `DEVRULES.md`
  forbids. `OWNER-ACTIONS.md` §4b holds the prices.
- **No alert delivery.** Detection is built (§2.3); email and webhook stay deferred. There is no
  mail provider wired on AWS and no decision about who is on the distribution list.
- **No PDF report.** Epic 12's rendering half is out of scope. §3 builds the *recommendation
  producer* the roadmap needs; the printed artefact is separate work.
- **No revenue-uplift modelling.** The spec defers it and there is no data to ground it in.
- **No persisted cluster snapshots** until §2.1's threshold is measured and recorded.
- **No CRM write-back.** Read-only, per §8.8.
- **No support-desk connectors.** Zendesk, Intercom and Freshdesk stay deferred as spec §8 has
  them. G1's connection plumbing is built so they are additive later rather than a second
  invention.
- **No revenue figures imported.** `arr_band` only (§8.5). The revenue uplift model is a spec §9
  open question and is not answered here.
